# Full-debug census, relink profile, and fixes (September 28, 2026)

**Scope:** Bevy, Polars, and Nushell, with `-Cdebuginfo=2` and `CARGO_INCREMENTAL=1` in
every arm. This round measured what the compressed layout still stores, where relinks
spend time, and how much a compact member index could skip. It also produced several
fixes. Local prototype numbers only; not upstream behavior.

## Headline

With a **release** Wild and Zstd-compressed final DWARF in both arms, the compressed
layout (compact objects linked directly by Wild, compressed `.rmeta`, compressed
incremental state) retains **69–77% less** than ordinary artifacts:

| Project | Ordinary | Compressed | Saved | Clean build | Example edit | Library edit | Final link |
|---|---:|---:|---:|---:|---:|---:|---:|
| Bevy | 13.029 GiB | 3.385 GiB | 74.0% | 122.8 → 136.7 s | 3.4 → 4.6 s | 10.3 → 12.4 s | 1.90 → 3.13 s |
| Polars | 8.341 GiB | 1.900 GiB | 77.2% | 79.4 → 86.4 s | 1.7 → 2.7 s | 1.8 → 2.9 s | 1.06 → 1.74 s |
| Nushell | 6.333 GiB | 1.964 GiB | 69.0% | 94.6 → 101.2 s | 2.0 → 3.2 s | 7.7 → 9.9 s | 0.96 → 1.64 s |

Costs: clean builds take 7–11% longer; each relink takes 0.6–1.2 s longer; peak
concurrent rustc RSS rises 0.4–0.8 GiB and Wild RSS 0.2–0.5 GiB. Edit times are means of
two example edits (the example crate only) and two library edits (a new public item in
`bevy_pbr`, `polars-lazy`, or `nu-command`, so the crate and its dependents rebuild).
Single runs per phase; not confidence intervals.

## Corrections to earlier reports

- **Earlier Wild timings used an unoptimized linker.** The recorded Bevy runs linked
  with `/wild/target/debug/wild` (Wild's dev profile has no optimization). That
  inflated every link, and with it the "direct path is 47–75% slower" edit results in
  [full-debug-incremental-results.md](full-debug-incremental-results.md). With a release
  Wild, a Bevy example edit takes 4.6 s compressed versus 3.4 s ordinary, not 29–35 s.
- **Library edits exposed a paged-graph thrash.** Earlier edits only touched the
  example crate. Recompiling a large crate with the 64 MiB page and 8 MiB index-bucket
  cache defaults re-read and re-decoded a graph page for most lookups: a Bevy library
  edit took **870 s**. Fixed (below): 10–12 s.

## Fixes made in this round

| Change | Where | Result |
|---|---|---|
| Stop evicting decoded graph pages and index buckets (later: remove the limit and its env vars entirely) | rustc `dep_graph/serialized.rs` | Bevy library edit 870 s → 12 s |
| Reverse index stores a 32-bit hash tag (lookups already verify candidates against pages), delta-coded, LEB128 | rustc `dep_graph/serialized.rs` | Index bytes −43% on Bevy (0.372 → 0.212 GiB); target −4.5%; `tests/incremental` 174/174 |
| Relocatable compact library manifests (version 2): store-relative member names; store and metadata relative to the manifest; resolver searches ancestors and Cargo `deps/` | compact-artifact, rustc, Wild | Moved target and uplifted `target/debug/lib*.rlib` alias link and run ([test_relocation.sh](../../tools/compressed-artifacts/test_relocation.sh)); v1 still readable |
| Wild recomputed file offsets after debug compression without segment padding, shifting a writable segment in the file | Wild `compression.rs` | Nushell debug build segfaulted in `ld.so`; fixed, with a new `compressed-debug-tls` integration test (fails before, passes after). This is an upstream Wild bug, independent of the compact format |
| Wild reports objects whose payload is never read | compact-artifact | Used for the member-selection check |

Tried and reverted: decoding compressed query caches on demand. Sessions still decoded
98–100% of the chunks, because saving the new cache re-reads every still-valid result
from the old one. Times and RSS matched the eager reader.

## What the compressed target still holds

After a clean build (share of the compressed target):

| Category | Bevy | Polars | Nushell |
|---|---:|---:|---:|
| Incremental dep-graph pages | 1.119 (33%) | 0.608 (32%) | 0.448 (23%) |
| Compact object store (most objects shared with incremental work products) | 0.705 (21%) | 0.318 (17%) | 0.453 (23%) |
| Final executable (Zstd DWARF) | 0.632 (19%) | 0.436 (23%) | 0.330 (17%) |
| Proc-macro `.so` | 0.207 (6%) | 0.119 (6%) | 0.196 (10%) |
| Query cache | 0.231 (7%) | 0.133 (7%) | 0.108 (6%) |
| Dep-graph reverse index | 0.212 (6%) | 0.100 (5%) | 0.092 (5%) |
| `.rmeta` | 0.146 (4%) | 0.074 (4%) | 0.164 (8%) |
| **Total** | **3.388 GiB** | **1.900 GiB** | **1.964 GiB** |

The dependency graph (pages plus index) is the largest remaining item: 28–39%. In a
sampled `bevy_ecs` graph (2.09 M nodes), compressed page bytes split into edges 34%,
value fingerprints 21%, the key-fingerprint dictionary 17%, and per-node headers 8%.
A per-page value-fingerprint dictionary did not beat Zstd (17.3 vs 15.4 MiB), because
Zstd already collapses the repeats. Edges are the next target.

## Where a relink spends time

Wild `--time`, Bevy example edit (ms): ordinary — compress debug sections 997, write
408, merge strings 328; compressed — compress debug sections 1,281, **resolve sections
757** (compact block decoding), write 450, merge strings 375. Zstd DWARF compression
costs 0.5–1.3 s per relink in both layouts, the largest single phase. The compact format
adds 0.35–0.76 s of block decoding.

## Would a compact member index help?

Objects whose payload a link never reads:

| Link | Objects | Never read | Metadata never read | Link time |
|---|---:|---:|---:|---:|
| Bevy example | 10,991 | 1.3% | 0.1% | 3.12 s |
| Polars example | 4,544 | 1.8% | 0.1% | 1.71 s |
| Nushell `nu` | 6,689 | 2.5% | 0.3% | 1.61 s |
| `bevy_ecs` unit tests | 621 | 5.0% | 0.2% | 0.31 s |
| `nu-protocol` unit tests | 5,461 | 3.0% | 0.4% | 1.25 s |
| `polars` lib unit tests | 4,432 | **99.8%** | **99.9% (527 MiB)** | 0.10 s |

Main executables and most test binaries read nearly everything. A test binary that
touches little of its dependency graph is the exception: there, an index would skip
almost all metadata parsing, but that link already takes 0.1 s. The index is worth
building only for projects with many such thin test binaries.

## Next steps, by expected benefit

1. **Shrink dependency-graph edges** (the largest compressed page component). Measure
   how often edges point near the source node and whether stable-ID assignment can
   keep dependency neighborhoods close together.
2. **Reduce compact block decoding at relink** (0.35–0.76 s): decode blocks for sections
   that survive garbage collection only, or reuse decoded blocks across relinks.
3. **Paired repeats.** These are single runs. Re-run the ordinary and compressed arms
   several times, alternating order, before quoting timing differences.
