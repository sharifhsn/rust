# Wild integration research for compressed Rust artifacts

**Source cut-off:** 2026-09-27. Wild checkout inspected at commit [`995ac77d0e0febf7e04ec1aa236895f18a7adfff`](https://github.com/wild-linker/wild/commit/995ac77d0e0febf7e04ec1aa236895f18a7adfff), dated 2026-09-26. This is a source review; no code, build, or benchmark was run.

## Recommendation

Start with **compressed section payloads inside ordinary ELF relocatable objects**, preserving eager, ordinary ELF symbol and section metadata. Keep `.rlib` as a conventional `ar` archive whose members remain parseable ELF objects. This fits Wild’s current architecture far better than replacing archive members with whole-object compressed blobs.

Wild already defers symbol processing for optional archive members until resolution requests them, and it loads many section payloads only when needed. But it currently walks every archive member, identifies every regular object, parses each object, and indexes its symbols before resolution. A whole-object compressed member would therefore either be decompressed eagerly just to obtain that symbol index, or require a new compact side index plus new member ownership, lifetime, selection, and cache machinery. Even after selection, whole-object decoding expands sections that Wild might discard.

Section compression leaves the data Wild needs for its eager index available in the normal ELF layout. Once a member is selected, Wild can decompress only the sections it consumes. This directly targets avoidable payload bytes and avoids introducing a parallel archive/object representation as the first integration step.

## What Wild does today

Wild’s archive reader intentionally exposes member contents as borrowed slices. `InputRef` similarly holds a borrowed input byte slice, with optional archive-member metadata ([archive reader](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/archive.rs#L31-L87), [input references](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/input_data.rs#L96-L151)).

When an archive is loaded, `process_archive` iterates all members and identifies all regular object members before processing them ([`input_data.rs`](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/input_data.rs#L501-L547)). It then parses each object into a `ParsedInputObject` ([object parsing](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/input_data.rs#L783-L828), [ELF parser wrapper](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/parsing.rs#L207-L228)). Group creation and symbol database setup visit the loaded objects and build the symbol index before resolution ([group creation](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/grouping.rs#L124-L194), [symbol DB](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/symbol_db.rs#L386-L477)).

The later resolution phase does defer optional archive-member symbol processing and queues it when a file is requested ([optional object scheduling](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/resolution.rs#L302-L335), [file request](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/resolution.rs#L567-L601)). Section resolution also distinguishes loaded from not-yet-loaded data ([section resolution](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/resolution.rs#L1480-L1507), [section data state](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/resolution.rs#L1666-L1689)). The useful distinction is therefore: **archive member discovery and metadata parsing are eager; parts of symbol resolution and section-data loading are lazy.**

Wild already recognizes compressed ELF section data. Its ELF implementation checks the section compression header and decompresses section data into linker-owned arena memory or a copy destination ([ELF section data](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/elf.rs#L3184-L3259), [decompression implementation](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/elf.rs#L4070-L4115)). However, Wild’s current compression option is for **final output debug sections**, not a general producer path for compressed allocatable sections in input `.o` files or `.rlib` members ([compression options](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/args/elf.rs#L1233-L1245), [output compression](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/compression.rs#L76-L114)). Existing compressed-debug tests exercise debug-section behavior, not compressed allocatable payloads in native archive members; examples include `wild/tests/sources/elf/compressed-debug/` and `compressed-debug-merge/`.

## Suggested first representation

Use standard ELF `SHF_COMPRESSED` sections in `ET_REL` objects, leaving the ELF header, section-header table, symbol/string tables, relocations, groups/COMDAT, and other data required to build the symbol and section index directly readable. Preserve normal archive layout and regenerate the archive symbol index after rewriting members so conventional linkers still have their expected archive metadata.

Start with a narrowly selected set of ordinary payload sections, such as `.text*` and `.rodata*`, behind an opt-in profile. Leave `.eh_frame` and any sections consumed through raw, non-decompressing readers unchanged until each such path is audited. The format describes section data as independently compressed, and relocations refer to offsets in the logical uncompressed section. This matches a linker that decompresses a section before applying relocations. See the [System V ELF ABI, sections 3.4 and 3.7](https://gabi.xinuos.com/elf.pdf).

There is an ABI-version caveat. The published GABI v4.2 text restricts `SHF_COMPRESSED` use on allocated sections, while its v4.3 draft describes allowing it for allocatable sections in `ET_REL` and adds Zstandard. Treat allocated-section compression as a compatibility-sensitive feature, not settled universal support. LLVM LLD has input handling for compressed sections, including zlib and Zstandard ([LLD input-section implementation](https://github.com/llvm/llvm-project/blob/main/lld/ELF/InputSection.cpp)). GNU ld documentation prominently covers compressed **debug** sections; it is not evidence that every BFD linker accepts compressed allocated `ET_REL` input. Keep an ordinary-artifact fallback and verify each supported system linker before broad compiler emission.

Wild’s existing section decode path makes a small synthetic-input experiment plausible without a new archive format. The first code work should verify that a compressed allocatable section can pass through Wild’s actual relocation, merge, garbage-collection, and output paths. Some current consumers intentionally request raw data, so the fact that the generic decode helper exists is not proof that every section kind is safe to compress.

## Why not whole-object compression first

Whole-object compression is a poor first fit for the current load order:

- Wild must parse every archive member’s ELF metadata and symbols to construct its current symbol database. Without a side index, whole-object compression forces eager decompression at the point where the proposed representation was meant to save work.
- A side index must faithfully encode every symbol property that affects resolution, including binding, visibility, weak/strong precedence, versions, section association, and archive ordering. It must stay synchronized with each object and archive rewrite.
- On selection, decompressing an entire object reads payload sections that section-level loading might never need. Section-level compression cannot avoid expanding part of a single selected section, but it can avoid expanding separate unused sections.
- Replacing borrowed archive slices with decoded member buffers adds ownership and cache-lifetime rules. Wild currently retains input references in its linker arena and uses temporary arena members for decompression ([linker ownership](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/libwild/src/lib.rs#L151-L188)).

Reconsider a compact symbol/section side index only if measurement shows ELF metadata parsing or metadata bytes—not section payloads—dominate. Keep that design orthogonal to payload compression so it can be evaluated independently.

## Rust incremental compilation and CAS fit

Rust’s incremental compiler currently persists codegen work products as named files and links or copies them into the incremental cache ([`work_product.rs`](https://github.com/rust-lang/rust/blob/main/compiler/rustc_incremental/src/persist/work_product.rs)). That is CGU/work-product identity, not evidence of an existing content-addressed store shared with the linker. A CAS could deduplicate byte-identical object artifacts or let multiple consumers refer to one immutable blob, but it does not compress unique objects or remove compiler query state. It also does not eliminate materialization for ordinary external linkers that expect ELF files inside `.rlib` archives.

Treat CAS as a possible storage layer after measuring duplicate bytes, not as a prerequisite for Wild integration. Account for compiler version and flags, target, backend, path remapping and build-ID effects in reproducibility; design concurrency, integrity checks, retention and garbage collection; and check actual allocated storage rather than logical file sizes. A store key and the digest of bytes should remain distinct concepts if a work product can be rebuilt under different toolchain identities.

Rust crate metadata is a separate concern. The compiler serialization guide documents lazy `LazyValue`, `LazyArray`, and `LazyTable` structures with offsets ([rustc serialization guide](https://rustc-dev-guide.rust-lang.org/serialization.html)). Preserve their logical random access if metadata compression is pursued: use independently decodable blocks with a directly readable directory from logical ranges to compressed blocks, and a bounded decode cache. A single compressed metadata file would otherwise turn a small lazy read into whole-file inflation. Wild does not parse Rust `rmeta` metadata, so this is not a Wild linker change.

Deferred code generation or MIR-only archives are also distinct from compression. Wild maintainer David Lattimore’s 2024 article reports potential savings from skipping unused codegen and discusses compiler/linker integration and shared codegen caches ([“Speeding up rustc by being lazy,” 2024-06-05](https://davidlattimore.github.io/posts/2024/06/05/speeding-up-rustc-by-being-lazy.html)). The compiler-team MIR-only rlibs issue records a prototype, not a production-ready replacement for normal rlibs ([compiler-team issue #738, opened 2024-04-10](https://github.com/rust-lang/compiler-team/issues/738)). These approaches may save more than compression when substantial code is never needed, but they need separate feasibility and platform work.

Wild’s incremental-linking design article also explains that archive-member activation and section garbage collection complicate incremental state ([“Designing Wild’s incremental linking,” 2024-11-19](https://davidlattimore.github.io/posts/2024/11/19/designing-wilds-incremental-linking.html)). Wild’s README at the inspected commit still says incremental linking is not implemented ([README](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/README.md#L5-L8)). Compressed members should therefore be treated as stable inputs to a future incremental design, not as an assumption that incremental linking already reuses decoded sections.

## Validation gates

1. **Format and producer:** Create a small ordinary `ET_REL` fixture with one compressed allocatable section and one uncompressed symbol/relocation set. Verify headers, decompressed size/alignment, archive member boundaries, long names, duplicate names, and regenerated ar symbol index. Keep debug-only compression cases separate.
2. **Wild behavior:** Check that parsing and symbol indexing do not inflate payload sections. Instrument bytes read, bytes decompressed, and peak resident memory. Link fixtures that select and discard archive members, and selected members with retained and discarded sections. Verify relocations are applied to logical uncompressed offsets.
3. **Semantics:** Cover strong/weak and versioned symbols, visibility, `--whole-archive`, section GC, COMDAT/groups, merge strings, TLS, notes, Rust `.rustc` metadata, LTO/plugin members, and target-specific section types. Audit raw-section readers before expanding the set of compressed names.
4. **Interoperability:** Test Wild plus each supported external linker and tool that consumes the generated `.rlib`. Until allocated-section compatibility is established, make compressed artifacts opt-in and retain ordinary output as a selectable fallback.
5. **Workload evidence:** On identical large-project clean, warm, and leaf-edit workloads, report target-directory size, CAS/cache/temp storage, peak RSS, CPU time, link time, and incremental compile time. Separate archive discovery and metadata cost from bytes actually inflated. The prior local prototype’s retained-size savings and leaf-edit cost are workload-specific; section-level decompression is a hypothesis to reduce extra edit work and needs a controlled rerun.

## Upstream process

Wild’s [`CONTRIBUTING.md`](https://github.com/wild-linker/wild/blob/995ac77d0e0febf7e04ec1aa236895f18a7adfff/CONTRIBUTING.md) asks prospective contributors to reach out to avoid duplicate work and says contributors should understand and author their own upstream communication. No maintainer contact or public post was made for this research. Before a broad change, have the project author send a short human-written question describing the proposed standard input representation, the intended producer, and the compatibility gate. Rust-side compiler or artifact-format changes should separately follow the relevant Rust compiler contribution process.
