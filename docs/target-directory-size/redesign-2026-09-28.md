# Graph, DWARF, and linking redesign (September 28, 2026, second round)

**Scope:** follow-up to the [first September 28 census](census-2026-09-28.md). Every idea
it listed was implemented or measured, except incremental relinking in Wild (left to
Wild's own work). All arms keep `debug = 2` and incremental compilation on. Local prototype
numbers only; single runs on a shared host.

## Result

Final census, same harness and phases as before (clean, touch, two example edits, two
library edits), release Wild, Zstd final DWARF in both arms:

| Project | Ordinary | Compressed | Saved | Compressed, first round | Final link, ordinary → compressed |
|---|---:|---:|---:|---:|---:|
| Bevy | 12.514 GiB | **2.582 GiB** | 79.4% | 3.385 GiB | 3.83 → 1.05 s |
| Polars | 8.145 GiB | **1.489 GiB** | 81.7% | 1.900 GiB | 1.21 → 0.64 s |
| Nushell | 5.850 GiB | **1.498 GiB** | 74.4% | 1.964 GiB | 1.18 → 0.65 s |

The compressed layout is now also faster to relink than ordinary artifacts. Example edits
take 2.5 vs 5.9 s (Bevy), 1.5 vs 1.7 s (Polars), and 2.3 vs 2.3 s (Nushell). Library edits
take 12.6 vs 15.8 s, 1.8 vs 2.1 s, and 10.0 vs 9.1 s. Peak Wild RSS fell to 1.4–2.5 GiB
(ordinary: 3.3–7.2 GiB). The remaining cost is clean builds, which are 9–22% slower, and
peak rustc RSS, which is about 0.5–0.6 GiB higher for Bevy and Nushell (unchanged for
Polars). Another session's process was using one host
core during this run, so compare arms within it rather than with earlier runs. gdb resolved
line info in every arm. The type lookups succeeded for Bevy and Nushell and failed
identically in both Polars arms, so the lookup string is at fault, not the layout.

## What changed, and what each part was worth

Nushell (compressed layout) isolates the contributions:

| Step | Target | Change |
|---|---:|---:|
| First-round compressed layout | 1.964 GiB | — |
| Proc macros and build scripts keep Cargo's default of no debug info (the harness had forced `-Cdebuginfo=2` onto them) | 1.814 GiB | −7.6% |
| Dependency graph: reverse index rebuilt in memory, column page layout, dependency-ordered IDs | 1.674 GiB | −7.7% (incremental directory −22%) |
| One copy of split DWARF, compressed `.dwo`, abstract-only linkage names | 1.499 GiB | −10.5% |

- **Reverse index in memory.** A recompiling crate loads every graph page anyway (Bevy's
  `bevy_pbr` loaded 735/735 pages and 1,024/1,024 index buckets for a plain touch), so the
  lookup table is built from the pages on first use instead of being stored.
- **Column page layout and dependency-ordered IDs.** An offline simulation on sampled Bevy
  graphs predicted 4–6% from columns and 12–17% with both, because 74–79% of edges had
  pointed far away. The graph cache limits were also removed.
- **One copy of DWARF.** With `-Csplit-debuginfo=unpacked`, rustc had stored each `.dwo`
  three ways: in `target/debug/deps` (where skeleton units point debuggers), hard-linked in
  the incremental cache, and again as a compact-library member. Compact manifests now omit
  `.dwo` members (packed split DWARF is rejected with compact artifacts), and `.dwo` work
  products stay hard-linked. Objects shrink to skeletons, and Wild no longer copies or
  compresses most DWARF, which is why relinks got faster.
- **gdb compatibility.** BFD (gdb 13.1 and 16.3) rejects a compressed section more than
  about ten times the size of its file, which 35 of 7,408 Nushell `.dwo` files hit.
  rustc now extends such a file with a trailing hole (no disk blocks, readable by gdb).
  Storing those sections uncompressed instead added 0.06 GiB on Nushell.

## Measured and not adopted

| Idea | Result |
|---|---|
| DWARF type units (`-generate-type-units`) as a deduplication mechanism | Target +16% (objects grow; linking doesn't recover it), clean build ~2× slower |
| `dwz`-style deduplication of the linked executable | Saves ~25% of the executable's compressed DWARF, but one-copy split DWARF already removed most of that DWARF from the executable. Cross-`.dwo` duplication (0.13–0.33 GiB) would need packing, which conflicts with per-CGU incremental reuse |
| Dynamic dependency linking (Bevy `dynamic_linking`) | Example edits 2–3× faster (0.75–1.0 s), but target +17% and `bevy_pbr` library edits 3.7× slower (35.8 s), because the 772 MiB Bevy dylib relinks. A tradeoff, not a win |
| Per-page dictionary for value fingerprints | Loses to Zstd (17.3 vs 15.4 MiB on a sampled graph) |
| Deduplicating identical edge lists | 44–54% of nodes share a list, but only 13% of edge bytes would go |

## What remains

In the compressed target: dependency-graph pages 26–38%, the final executable 14–21%
(skeleton DWARF, line tables, symbols, code), `.dwo` files 9–13%, the object store 9–13%,
and the query cache 7–9%. The graph is still the largest single item. The next steps are
the clean-build regression (profile rustc's debug-info compression and `.dwo` writing),
then graph value fingerprints and edges, then the executable's line tables and symbols.
